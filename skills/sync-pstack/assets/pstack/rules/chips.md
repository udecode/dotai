# Suggested tasks

This file says how the lead offers, records and cleans up suggested tasks. The pstack block in `AGENTS.md` points here. The `sync-pstack` skill renders this file from its shared source in `udecode/dotai`, so change it there.

- **Suggested tasks.** Every runtime follows this rule. A suggested task is side work outside the run's target that the owner can start in a new session. A finding that pivots the run never becomes one, as the Autopilot rule says. Sessions started from these tasks are the owner's own work in this checkout, so overlap with them is this rule's subject, not something the Other sessions rule dismisses.
  - **Ledger.** A task lives as rows in the project's ledger `<plans>/suggested-tasks.decisions.tsv`, under one id it keeps for good, because a task outlives the run that offered it and every card that showed it. A card in a suggest tool, such as Claude Code desktop's `spawn_task` or `start_session`, is only a view of a task. The lead queues and appends ledger rows like any other decision-log row, with phase `chip`, and never in a run's own log.
    - The decision is `<task id> <title>`, repeated unchanged on every later row. A new task takes its id from `node .agents/pstack/decisions-check.mjs chips id`. The card's own id goes in a `card:` token, never in the decision.
    - `node .agents/pstack/decisions-check.mjs chips` prints every open task as Ready, Started, Waiting or Unmigrated, with what each waits on and the checks it owns, then the tasks a dropped card closed as `gone`, the topics with more than one task or a design question, and a Do list. It exits 1 when the Do list holds a problem: a card on a task that cannot start, a wait that can never clear, or two open design questions in one topic. `chips --fetch` first runs `git fetch --all`, which refreshes the remote branches that PR waits read. `chips --session <id>` names this session, so the Do list asks to check each card another session holds; without it, every card counts as this session's. `chips brief <id>` prints the prompt a card for that task carries.
  - **Title.** The title is an imperative phrase. It ends in ` (xhigh)` when the task runs a whole poteto playbook with design judgment, such as an architecture, API or plan choice, a bug whose cause is unknown or a performance diagnosis. A task that says exactly what to do, such as a named fix, a doc update or a check, has a plain title and runs at `high`. The title keeps `(xhigh)` whatever the project allows, so the owner sees the recommendation. No title says when the task can start, because `chips` works that out on every read; `append` refuses a new offer whose title says `Now:` or `After:` or ends in `(high)`.
    - When the suggest tool has an effort setting, such as `start_session`'s `effort` for a task that starts fresh, the card sets it, because a card offered without one runs at the lead's own effort. It passes the title's effort, lowered to the highest level any role runs at in the current runtime's pstack models sheet once the project's own effort rules apply. A project rule that runs no role above `high` makes every card pass `high`, even under an `xhigh` title. When the tool refuses that level, such as one above the lead's own, the card passes the nearest level the tool takes. The owner can raise the setting on the card.
  - **Offer.** Run `chips` before offering. When the finding belongs to the question an offered task's topic names, log it as a `folded` row on that task, with `writes:`, `waits:` and `owns:` listing what it adds, instead of offering a new task. When it belongs to a started task's question, offer a new task that waits on the started one with `task:`, because a started session keeps its own plan. Otherwise the offer's evidence holds these tokens, each `key: value`, named once and separated by semicolons, and its result is `offered`:
    - `writes: <path>, <path>`, required, each a repository path or directory, or an absolute path in another checkout, with no whitespace, glob, quote, comma or semicolon;
    - `topic: <name>`, required, one lowercase kebab-case name for the owner question, such as `plite-landing`, never an area such as `core` or `pstack`; reuse a topic `chips` lists when the finding belongs to its question;
    - `kind: decide` when the task settles a design question before any fix, and nothing or `kind: fix` otherwise; a topic holds at most one offered `decide` task, and while its design question is started, a new one on that topic waits on it with `task:`;
    - `waits: <wait>, <wait>`, one for each thing the task needs first, never the task itself. `pr:<number>` clears when a commit subject starts `Merge pull request #<number> from` or ends in `(#<number>)`. `chips` reads those subjects on `refs/remotes/<remote>/<branch>` as last fetched, for each remote `git remote` lists, where `<branch>` is the `branch` in `.agents/pstack.json`. With no `branch` there, any remote branch counts. A PR that was closed or rebase-merged never clears it, so the lead logs `updated` with the waits the task has now. `task:<id>` clears when that task lands or is dismissed `done`, following each `dup` to the task it merged into. `run:<plan path>` clears when that plan's `Status:` says it landed, such as `done` or `executed`. A task or plan that closes any other way, such as superseded or cancelled, and a task wait that loops back to the task through the waits of offered tasks, leave the wait stuck, and `chips` asks for an `updated` row. A started task's waits no longer count. A task that needs the current run's result waits on `run:` with the run's plan, and a wait never goes in the title or the why;
    - `owns: <check>, <check>` when the task fixes a check that fails on the base branch, such as `ci:check`.
  - **Cards.** Only a task that `chips` lists as Ready before its card gets one. A task is Ready when it has a topic, each of its waits has cleared and no started task writes an overlapping path. `chips` reads the tasks that have a card first, then the rest, each group in ledger order, and a task that writes a path an earlier Ready task writes waits behind it; a waiting task holds no paths. The card's prompt is `chips brief <id>`. The lead adds a card only while the suggest tool's last result lists fewer than 20 pending cards, because a newer card pushes the oldest out; a session that has not offered a card yet has none pending. After each card it logs `carded` with `card: <tool id>` and `session: <id>`. The session id is the one the runtime's session tool gives this session, such as Claude Code desktop's `get_session` with `self`, because a card goes away with the session that offered it.
    - When a card leaves the queue without the owner starting or dismissing it, such as when a newer card pushes it out or its session ends, the lead logs `uncarded`, and the task stays open; `chips` lists it as Ready again. Limits says how the lead tells those cases apart. For a card whose session ended, a later session's sweep logs it, as Sweep says. When the dismiss tool or the owner says the owner dismissed the card, the lead logs `dismissed declined`. Before any other dismissal of a task whose card this session holds, the lead withdraws the card.
  - **Later rows.** A later row's result is one of these, and it takes only the tokens named here:
    - `started`, with `writes:` for any path it adds. The session a card started logs it before it writes, and the lead logs it when the dismiss tool reports that the owner already started the task, or when the owner says so;
    - `landed` when the started session reports its change done, the owner says so, or a commit holds the change; a half-written change in the tree does not count;
    - `updated`, on an offered task, when its paths, topic, kind, waits or owned checks change, and on a started task only for its owned checks; the row names only the tokens that change, and each replaces that token's whole list;
    - `folded` on an offered task, with `writes:`, `waits:` and `owns:` that join the task's own; `carded` with `card:` and `session:`; or `uncarded`, as Offer and Cards say;
    - `reopened` for a task that an older ledger closed as `gone` when its card left the queue, while its work is still owed;
    - `dismissed` with one reason: `done` when the tree already holds the fix of a task nobody started; `dup <task id>` when another open task covers a task nobody started. The row moves its title, findings, paths, waits and owned checks into the kept task, makes the kept task `decide` when either one is, and drops every wait that now leads back to the kept task. A started kept task takes only the title, findings and checks; `superseded` when the run removed the target of a task nobody started; `declined` when the owner dismissed its card or said to drop it; or `stopped` when the owner says they stopped a started task's session before its change landed.
  - **Checks.** `decisions-check.mjs` judges each chip row against the ledger rows before it. Both `append` and the whole-log check, which skips rows committed at `HEAD`, refuse:
    - a chip row in a run's log, a second offer of one id, or a later row whose task's state does not allow it;
    - an offer with no `writes:`, a `writes:`, `topic:`, `kind:`, `waits:`, `owns:` or `session:` value outside the grammar Offer and Cards give, an `updated` row that names no token, an `updated` row on a started task that names anything but `owns:`, or a `carded` row with no `card:`;
    - a `dup` that names the task itself or a task that is not open;
    - an offer, `updated`, `reopened` or `dismissed dup` row that leaves two offered `decide` tasks in one topic, or an offered `decide` task that does not wait on its topic's started one.
    - Only `append` also refuses the rows below. Each one judges a rule that older ledgers predate, or the live state of git, plans, the ledger or the paths on disk, which can change after the row is written: a new offer with no `topic:` or with a title marked `Now:`, `After:` or `(high)`; a new `dismissed gone` or `dismissed replaced` row; a `topic:`, `kind:`, `card:` or `session:` named twice, or a token the row's result does not take; a task that waits on itself, directly or through a `dup`; a `started` row that adds a path another started task writes; a `card:` with no `session:`, or an offer with `session:` and no `card:`; a `carded` row, or an offer with `card:`, for a task `chips` would not list as Ready without that card; and, in any log, a `base-red:` token that names a check no open ledger task lists in its `owns:`.
  - **Sweep.** The lead runs `chips` before it offers a task, at each hand-back, after each compaction and at the close. It applies the Do list, its card items included, and the steps below in one `append --from` batch:
    - When the tree already holds an offered task's fix, the lead logs `dismissed done`. When a started task's change has landed, it logs `landed`. When the run removed a task's target, it logs `dismissed superseded`.
    - When open tasks nobody started answer one question, the lead keeps the earliest and logs each other one `dismissed dup <kept id>`. When a started session's plan already holds the work of a task nobody started, the lead logs that task `dismissed dup` with the started task's id.
    - Where the runtime's session tool gives this session's id, the lead runs `chips --session <id>` with it. For each card the Do list says another session holds, it looks that session up with the session tool and logs `uncarded` when the tool reports it archived or gone. A runtime without a session tool logs `uncarded` for a card on the owner's word that its session ended.
    - For each task `chips` lists as Lost, which a dropped card closed as `gone`, the lead logs `reopened`, then `updated` with its topic and waits, or, when its work is already done or its target gone, `dismissed done` or `dismissed superseded` after the reopen.
    - Before the run writes a path that an offered task writes, the lead logs `updated` on that task with its waits plus `run:<the run's plan>`. When the task has a card, the lead first withdraws the card and logs `uncarded`; when the tool reports the owner already started it, the lead logs `started` instead.
    - Before the run writes a path a started task writes, the lead waits for that task to land or leaves that path to it. The lead runs both checks whenever the run is about to widen what it writes, not only at a sweep.
    - A session started from a task finds its own row by the id in its brief and skips it in these checks. It runs `chips` first, and when its task is no longer Ready, it tells the owner what the task waits on before it writes. Before it writes a path its task does not list, it logs another `started` row whose `writes:` lists the added paths. When `append` refuses that row because another started task writes the path, the session leaves that path alone and tells the owner.
  - **Base branch.** A decision row that blames a failing check on the base branch, rather than on the run, names that check in its evidence as `base-red: <check>`, such as `base-red: ci:check`. Before that row, an open ledger task must list the check in `owns:`. The lead reuses a check name `chips` already shows when it names the same failure, and otherwise offers a task that owns it, such as `Make the base branch green (xhigh)`, or logs `updated` with the whole `owns:` list on the task that already covers it, started or not. A row once appended stays valid after its owning task lands.
  - **Limits.** The tool cannot rename a card or change its prompt, so the lead withdraws a card whose task changed, logs `uncarded` and cards the task again from `chips brief`. The dismiss tool works only in the session that offered the card. It withdraws a card the owner has not acted on, and for one the owner started or dismissed, it reports which. A suggest tool result that lists the cards still pending in this session, such as an offer's, shows which left, and a card the owner clicked or dismissed leaves that list too. So after each such result, for each task this session carded that is missing from that list and that `chips` does not show started, the lead calls the dismiss tool on its card. It logs `started` when the tool reports the owner started it, `dismissed declined` when the tool reports the owner dismissed it, and `uncarded` otherwise. It leaves a card another session offered alone while that session lives, as Sweep says; that card's prompt has the session check the task before it writes. A runtime without a suggest tool skips Cards. It lists each Ready task in the plan's `## Open work` as `<id> <title>`, with `owner:` the owner, `stop:` started or dismissed and the ledger as where it is tracked, or in its reply when the run has no plan. It learns that a task started or stopped only from the owner.
  - **Close.** At the close, once the plan's `Status:` says done, which clears every `run:` wait on it, the lead runs the sweep once more and cards each Ready task that has no card while fewer than 20 cards are pending; `chips` keeps listing the rest. A runtime without a suggest tool first writes that Open work, before it changes the `Status:`, counting as Ready each task whose only blocker on the `chips` board is `run:` with this plan.
