# Planning and execution batches

A plan is working state. Reuse the existing plan for the same outcome. Small changes need no new document. For sustained work, record:

- Objective and observable completion threshold.
- Source authority, requested scope, human assignments and publication boundaries.
- Acceptance IDs with source links and exact proof required.
- Current decisions, evidence, unresolved risks and next action.
- Pause state, actual deadline or iteration budget when the user supplied one.

Use the project-owned plan template when present. Shared `autogoal` assets only seed missing templates; never overwrite a project's template to refresh a skill. Link detailed ledgers instead of duplicating them. Update the current checkpoint at settled batches or material changes; command chronology is not a second plan.

For a migration, name each complete caller set, observable operation, invariant, deletion boundary and recovery condition. Resolve the riskiest unknown with bounded research or measurement before building on it. Use an architecture method while the choice is unresolved; preserve an accepted choice until evidence invalidates it.

Before a multi-outcome batch, name its owner, acceptance IDs, remaining portions, required proof and safe exit. Finish coupled implementation before final proof. One capture can support several claims only if it actually proves each fact under matching bindings.

Visit unvisited eligible owners before revisiting parked work. A new idea alone does not reopen a human-blocked owner. At settled checkpoints distinguish verified, awaiting human help, unfinished and unvisited counts; their sum must equal the declared denominator. Two checkpoints without advancing acceptance or disposition call for reassessing the next owner, not adding paperwork.

Do not confuse completed iteration accounting with product completion. A deadline is an upper bound, not a requirement to consume time; preserve unfinished acceptance when it expires. Set a native token budget only when the user explicitly requested one.

Plan-only permits investigation and a reviewable implementation plan, then stops. An audit executes inspection; it is not plan-only. Neither permits product changes or publication by implication.
